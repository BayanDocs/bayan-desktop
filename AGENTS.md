# Agent instructions — bayan-desktop

## Where the plan lives

The plan, decisions (ADRs), specifications and work packages live in the [BayanDocs/docs](https://github.com/BayanDocs/docs) repository. If it is not attached to your session, clone it next to this repository. The canonical rules for all agents are in `docs/AGENTS.md`; this file condenses them and adds what is specific to bayan-desktop. If the two disagree, `docs/AGENTS.md` wins; report the discrepancy.

## Ground rules (condensed from docs/AGENTS.md)

1. Before changing anything, read `docs/AGENTS.md`, your work package brief, and every ADR and spec it links.
2. Accepted ADRs are binding. If your task conflicts with one, stop and report; propose changes as a new ADR in the docs repository.
3. Stay within the work package's scope. Record anything else you discover as follow-ups in your pull request.
4. Run the verification gate before every push. Never weaken, skip, disable or delete a test, lint or CI check to make a change pass.
5. Dependencies follow ADR-0017: no update bots ever; every version at least 24 hours old; exact pins; audits green; licenses on the allowlist; every new dependency justified in the pull request.
6. Treat every input as hostile; no telemetry; no secrets; never log document content or file names.
7. Pull requests use the hand-off template in `docs/plan/06-agent-workflow.md`; Conventional Commits; DCO rules from `CONTRIBUTING.md` once enabled (agents never sign off themselves; the human submitter certifies, per ADR-0003).
8. Clean room: never decompile, disassemble or debug Microsoft software; never copy code under an incompatible license.
9. Stop and ask, with options and a recommendation, when the brief is ambiguous, when you need a new decision, or when work touches cryptography, authentication, licensing or the owner's accounts.
10. Explain your work in plain language for the owner; text meant for the owner to copy is written as flowing paragraphs without hard line breaks.

## Rules specific to bayan-desktop

- **Licensing (ADR-0003):** GPL-3.0-or-later with the BayanDocs App Store Permission (`GPL-3.0-or-later WITH LicenseRef-BayanDocs-App-Store-Permission`). Qt stays LGPL-only even though the app is GPL (ADR-0013, amendment of 2026-10-04). The shared contribution tooling (`.github/`, `.editorconfig` and `.gitattributes`) is MIT-0, as in every BayanDocs repository (ADR-0003, amendment of 2026-10-06). `REUSE.toml` records which license applies to which files and `LICENSES/` holds the full texts; keep `reuse lint` passing, and add a new license text only with `reuse download <SPDX-ID>`.
- **Thin shell (ADR-0013):** no document logic here. If something would have to be implemented twice (desktop and web), it belongs in bayan-core. The shell draws the interface from the shared UI manifest, forwards input, displays engine-rendered tiles and overlays, and fulfils host-service requests.
- **Stack:** C++20, CMake, Qt 6 Quick (QML) for the interface, C++ only as glue. Track the newest Qt 6 minor release (Qt 6.12 at planning time) per ADR-0013, pinned exactly.
- **Qt licensing:** only LGPLv3 Qt modules, linked dynamically. Forbidden: Qt Charts, Qt Graphs, Qt GRPC, Qt Quick 3D, Qt Virtual Keyboard, Qt Canvas Painter and any other GPL-only or commercial-only module or tool. Compile QML with `qmlcachegen`, not the commercial `qmlsc`.
- **No other C++ dependencies** besides Qt (Qt Test for tests) without an ADR amendment.
- **Untrusted data stays in the engine (ADR-0006):** never use Qt to decode document content, embedded images, document fonts or clipboard payloads; pass raw bytes to the engine.
- **Engine boundary (ADR-0012):** talk to the engine only through the C ABI and the JSON protocol in `docs/specs/engine-protocol.md`. Engine callbacks arrive on the engine thread; marshal them to the Qt main thread and never call back into the engine synchronously from a callback.
- **Accessibility and input methods are features, not polish (ADR-0020):** every change to the canvas keeps screen-reader and IME support working.

## Verification gate

Install the pinned tools once per machine or session with `scripts/dev-setup.sh` (CMake, Ninja, clang-format and clang-tidy from `deps/requirements-tools.txt`, and Qt from `deps/qt.json` unless a matching Qt is already installed), then load the environment it prints (`. ~/.local/share/bayandocs/desktop-tools/env.sh`). The gate is one command, run from the repository root before every push:

```sh
cmake --workflow --preset verify
```

It configures an optimized build with warnings as errors and the Qt licensing check, builds, runs clang-format, clang-tidy and qmllint, and runs every test: the engine wrapper tests, the tests of the engine's C interface (`engine.c_interface`: what the stub must do as the real engine does, and every kind of message the engine sends checked against the protocol's JSON Schema), the unit tests of the shell's logic (`unit.*`: protocol parsing, tile arithmetic and cache, key and input-method translation, accessible text, the allowance of restarts after engine failures, and the tests' checker of the protocol's JSON Schema), the document session tests, the document canvas tests in a window and the interface tests, which load the QML interface (`app.*`, the canvas at 100 % and 125 %), the headless smoke test (`bayan-desktop --smoke-test` with the offscreen platform plugin), the Qt licensing policy tests, the Qt installer's tests, the Qt release-age check (`supply_chain.qt_release_age`, with its tests), which reads the Git history and so fails in a shallow clone (`git fetch --unshallow`), and the checks of the Ubuntu packages of the Linux CI jobs (`supply_chain.ubuntu_packages_lock`: `deps/ubuntu-packages.lock` is well formed, its snapshot date is not before its base image was created, it configures every package it unpacks, every job that installs it runs in its base image, and no workflow runs apt; and, on Linux, `supply_chain.ubuntu_packages_script`, the tests of `scripts/ubuntu-packages.sh`, which need curl and openssl). CI also runs `cmake --workflow --preset asan` (AddressSanitizer and UndefinedBehaviorSanitizer, Linux, every test against the stub) and, in the same job, the tests that use the engine against the real engine under both sanitizers (`scripts/test-engine-sdk.sh --sdk build/bayan-core-sdk --sanitizers`, the `engine-sdk-asan` preset), `cmake --workflow --preset ci` on macOS and `cmake --workflow --preset msvc` on Windows (from an x64 Visual Studio developer environment), and on every operating system the tests that use the engine against a stand-in SDK and against the real engine (see the notes below). `cmake --workflow --preset dev` is the quick Debug build and test, and `cmake --build --preset verify --target format` fixes formatting. Five more workflows run on every pull request, as in every BayanDocs repository: the DCO check (`.github/workflows/dco.yml`; the rules are in `CONTRIBUTING.md`), `reuse lint` (`.github/workflows/reuse.yml`), the supply-chain checks (`.github/workflows/supply-chain.yml`, also nightly), which fail when configuration for an update bot such as Dependabot or Renovate appears (ADR-0017 rule 1) and audit the hash-pinned Python tools of CI with pip-audit, `deps/requirements-tools.txt` included, the workflow lint (`.github/workflows/workflow-lint.yml`, also nightly) and CodeQL (`.github/workflows/codeql.yml`, also weekly), which "Workflow conventions" below describes. All five run the pull request's own copy of their files, so a pull request can change the checks that judge it: treat every change under `.github/` as security-relevant in review.

Notes for agents: the default build links the stub engine in `src/engine/stub/` (`BAYAN_ENGINE=stub`), whose single test page has no editable text and no accessibility tree. `src/engine/stub/include/bayan_ffi.h` and `src/engine/stub/schema/engine-protocol.schema.json` are byte-for-byte copies of the C SDK's generated header and of the protocol's JSON Schema, from the bayan-core commit pinned in `deps/bayan-core.json`: never edit them; the test `engine.sdk_copies` compares them with the SDK's whenever the app is built against one, and `src/engine/README.md` says how to update them when the pin moves. The stub does what that header documents, as the real engine does (tiles rendered on the engine thread in order with the messages posted before them, `BAYAN_STATUS_WRONG_THREAD` inside any engine's callback). Tests hand the shell messages as if from the engine only through `tests/support/enginemessages.h`, which checks each against the schema with the strict checker of `tests/support/protocolschema.h` (written with Qt's JSON classes: no JSON Schema library, ADR-0017), deliberately broken input only through its `deliverMalformed()`, which takes only input broken in exactly the one place the test names; a schema keyword the checker does not implement makes the tests fail, so extend the checker when a newer schema needs it. Like the real engine, the stub fails on `diag.panic` when created with the test switch `test.allow_panic`, so the tests of the recovery after engine failures (engine protocol §12.1) run against both engines; its other test switches are described at the top of `src/engine/stub/bayan_engine_stub.cpp`. The real engine is bayan-core's C SDK (CORE-007): `scripts/build-engine-sdk.sh` builds it from the commit pinned in `deps/bayan-core.json` into `build/bayan-core-sdk` (it needs rustup, and on Windows must run outside the Visual Studio developer environment), and `scripts/test-engine-sdk.sh --sdk build/bayan-core-sdk` builds the app against it and runs the tests that use the engine. Without `--sdk`, `scripts/test-engine-sdk.sh` builds the stub as a stand-in SDK and tests against that. CI runs both on every operating system, the real one with `BAYAN_REQUIRE_MOCK_DOCUMENT=1`, which makes the tests that need the real engine's mock document fail instead of skip; with the stub they skip. `src/engine/README.md` describes the SDK layout the build expects (`BAYAN_ENGINE=sdk`, `BAYAN_ENGINE_SDK_DIR=<path>`, workflow presets `engine-sdk` and `engine-sdk-msvc`). Test input-method and accessibility changes against the real engine, and run `bayan-desktop --benchmark <file>` when you change how the canvas draws (see `docs/spikes/DESK-002-report.md`). Use `bayan_find_qt()` instead of `find_package(Qt6 ...)`; a new Qt module must be reviewed and added to the allowlist in `cmake/BayanQtPolicy.cmake`.

## Workflow conventions

GitHub Actions workflows run with access to the repository, so they are part of the supply chain (threat T16 in `docs/specs/threat-model.md`). Every workflow follows the workflow conventions of `docs/AGENTS.md` (§6, from work package X-002):

- **Permissions:** `permissions: {}` at the top of the workflow, and each job asks in its own `permissions:` block for exactly what it needs, with a comment that says why. Most jobs need only `contents: read`.
- **Write permissions:** a job that runs code of the repository, of its tools or of its dependencies never holds a write permission, because any program that runs in a job can get hold of the job's token. When such a job's results must be written somewhere, for example uploaded to code scanning, it keeps them as a workflow artifact with a short retention, which holds nothing else (anyone signed in to GitHub can download a public repository's artifacts), and a separate job holds the write permission and writes them. That job's steps are GitHub's own actions and, if it is a required check, a first step that fails unless the job whose results it writes succeeded; such a check runs with `if: ${{ !cancelled() }}`, because GitHub skips a job whose `needs` failed and counts a skipped required check as passed. The CodeQL and Scorecard workflows work this way (work package X-004).
- **Checkout:** `persist-credentials: false` on every `actions/checkout`, unless the job pushes (none does today).
- **Triggers:** never `pull_request_target`, and never `workflow_run` to act on a pull request's code with more than read access. Workflows that pull requests trigger use no secrets; the automatic `GITHUB_TOKEN`, limited by the permissions above, is the only credential they get. A workflow with a job that `main`'s ruleset requires runs on `merge_group` (`types: [checks_requested]`) as well as on `pull_request`, under the same rules, because the merge queue waits for every required check on the commit it is about to merge, and a check that never runs there takes the pull request out of the queue after a timeout.
- **Limits:** every job has `timeout-minutes` and runs under a `concurrency` group (set once for the whole workflow), so that a newer push to a pull request replaces the older run instead of running beside it.
- **Actions:** only GitHub's own actions (`actions/*`, `github/*`), each pinned to a full 40-character commit SHA with its version in a trailing comment (`uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`), and published at least 24 hours earlier. A third-party action needs the owner's approval and an entry in the allowed list of `docs/scripts/github-settings.py`; prefer a checksum-verified program instead, as the Scorecard workflow does.
- **Tools:** every tool that a workflow downloads is pinned to an exact version that was at least 24 hours old, and is checked against a SHA-256 written in the repository (taken from the publisher's checksum file where there is one) before it runs. Python tools come from hash-pinned requirements files (`pip --require-hashes --only-binary :all:`). Never `curl … | sh`, never "latest".
- **Untrusted text:** never put `${{ … }}` with event data (pull request titles, branch names, commit messages) inside a `run:` script, where it would become shell code; pass it through `env:` and quote the variable.

Three workflows check this. **Workflow lint** (`.github/workflows/workflow-lint.yml`, on every pull request, on pushes to `main` and nightly) runs zizmor, a static analyser for workflows, which must report nothing at its default settings: it reads no configuration file, obeys no ignore comments and also audits workflows that a `.gitignore` names, and it runs its online audits, which find actions with known vulnerabilities. It also runs `pinact run --check --verify-min-age --min-age 1`, which checks every pin and its age. zizmor is pinned in `.github/workflow-lint/requirements.txt` and pinact in the workflow, both equal to the BayanDocs cloud environment's pins. **CodeQL** (`.github/workflows/codeql.yml`, on every pull request, on pushes to `main` and weekly) scans the workflows, the Python scripts and tests, and the C++ app and its tests; QML is not scanned, because CodeQL does not support it. Each language is analysed by a job with read permissions only (`CodeQL analysis (<language>)`), and `CodeQL (<language>)`, the required check, uploads its results to code scanning, as the rule on write permissions above asks. CodeQL reads C++ while it is compiled, so its C++ analysis job builds the app with the steps of `ci.yml`'s Linux job (in a container from the base image of `deps/ubuntu-packages.lock`, with the Ubuntu packages that the lock lists, the Qt release-age check, `scripts/dev-setup.sh`, the `ci` preset without the tests), using the container's Python 3. Its engine, the CodeQL bundle, is downloaded by the workflow and checked against the SHA-256 that its release publishes. **Scorecard** (`.github/workflows/scorecard.yml`, weekly and on pushes to `main`) runs the OpenSSF Scorecard program, pinned and checked against its SHA-256, with a read-only token, and rates the repository's practices; `.github/scorecard/policy.yml` chooses which of its checks raise alerts. CodeQL and Scorecard report under Security → Code scanning. In a BayanDocs cloud session, run `zizmor --offline --no-config --no-ignores --collect=all --strict-collection .` before pushing a workflow change: the session's network proxy refuses the online requests of zizmor and pinact, which the workflow-lint job of the pull request makes. `workflow-lint.yml`, `scorecard.yml`, `.github/workflow-lint/` and `.github/scorecard/` are identical in all five BayanDocs repositories: change them in all of them together.

## Dependency mechanisms

- **Qt:** the exact version, its release date and, for each platform, the repository path, package and archives to install are recorded in `deps/qt.json`. `scripts/install-qt.py` (Python standard library only; ADR-0017, amendment of 2026-10-04) downloads them from Qt's servers, checks each archive against the SHA-256 published on download.qt.io and every archive entry for unsafe paths and links, and extracts with the pinned CMake; `scripts/dev-setup.sh` runs it. When updating Qt, update every field of `deps/qt.json` (Qt's repository paths contain the version) and run `cmake --workflow --preset verify`, whose `install_qt` test covers the installer, its SHA-256 checks included (`test_refuses_an_archive_with_the_wrong_hash`, `test_refuses_an_index_with_the_wrong_hash`). `scripts/check-qt-release-age.py` (the `supply_chain.qt_release_age` test, in every CI job) fails unless the Qt release in `deps/qt.json` was at least 24 hours older than the commit that pinned that version, and than now (ADR-0017 rule 4). A date-only `qt_released` counts as the end of that day in UTC, so record the later of the release announcement and the `ReleaseDate` in Qt's repository index (`Updates.xml`). CI checks out the full history for it (`fetch-depth: 0`), and every CI job also runs it as a step of its own before it installs Qt, so that the tools of a Qt release that is too young never run in a build.
- **bayan-core (the real engine, for CI and tests):** during Phase 0, before bayan-core publishes SDK releases, CI builds its C SDK from source at the commit pinned in `deps/bayan-core.json` (the repository's URL, the full 40-character commit hash and the commit's date), as ADR-0002 §4 allows for Phase 0. `scripts/build-engine-sdk.sh` fetches exactly that commit and checks that it got it and that the commit is on bayan-core's `main` (GitHub serves the commits of a repository's forks through its own URL too), installs with rustup (in the Linux CI containers Ubuntu's rustup package, 1.26.0, from `deps/ubuntu-packages.lock`; on macOS and Windows the runner image's own) the Rust version that the commit pins in its `rust-toolchain.toml` (minimal profile: compiler, Cargo and standard library; `--no-self-update`, so rustup does not replace itself), and builds with `cargo xtask sdk`, which uses bayan-core's committed `Cargo.lock` with `--locked`: every crate is the version and checksum that bayan-core's own gate approved (exact pins, 24-hour minimum age, cargo deny). The pin always names a commit on bayan-core's `main`; move it when a work package needs a newer engine or in the monthly dependency session, copy the new SDK's `include/bayan_ffi.h` and `schema/engine-protocol.schema.json` over the copies in `src/engine/stub/` in the same commit (`engine.sdk_copies` fails until they match), and run `scripts/build-engine-sdk.sh` and `scripts/test-engine-sdk.sh --sdk build/bayan-core-sdk` before pushing. Unlike every other pin, that commit need not be 24 hours old, because it is bayan-core's own code from its `main`; the Rust version and the crates it brings in must be (ADR-0017, amendment of 2026-10-12). Shipped builds will use released SDKs pinned by version and SHA-256 instead (ADR-0002 §4).
- **Build and lint tools** (CMake, Ninja, clang-format, clang-tidy) are Python packages pinned to exact versions with SHA-256 hashes in `deps/requirements-tools.txt`; `scripts/dev-setup.sh` installs them with `pip --require-hashes --only-binary :all:`, so only verified prebuilt wheels are used and no package code runs at install time. The file's header records publish dates and the command that regenerates it. The supply-chain workflow audits the file with pip-audit on every pull request and nightly.
- **CI:** GitHub Actions are pinned to full commit SHAs with the version in a comment; Python is Ubuntu 24.04's Python 3 in the Linux containers (next bullet) and the runner image's own Python 3 on macOS and Windows, as in every BayanDocs workflow, so nothing is downloaded for it (each job of `ci.yml` checks that it is 3.11 or newer, prints its version and hands it to `scripts/dev-setup.sh`); the workflow-lint job checks the actions' pins and their age, and the tools that the workflow-lint, Scorecard and CodeQL workflows download (zizmor, pinact, Scorecard and the CodeQL bundle) are pinned by version and SHA-256 (see "Workflow conventions").
- **Ubuntu packages (the Linux CI jobs):** the jobs `linux` and `sanitizers` of `ci.yml` and `cpp-analysis` of `codeql.yml` run in a container from `buildpack-deps:noble-scm`, a Docker Official Image of Ubuntu 24.04 with ca-certificates, curl and git, pinned by digest, and install exactly the Ubuntu package files that `deps/ubuntu-packages.lock` lists (ADR-0017, amendment of 2026-11-05; work package X-005), so that neither a newer runner image nor one Ubuntu server being down can break them. The lock's header names the base image with its digest and creation time, the architecture (amd64), the snapshot date of Ubuntu's archive and the requested packages: the six -dev packages that Qt needs to build, `libglib2.0-0t64`, which Qt's own libraries link, and what the runner image used to supply (`g++`, `python3-venv`, `rustup`, `xz-utils`, and `zstd` for the CodeQL bundle). Then follows apt's plan for that base and date, which also upgrades the image's own packages that are newer at that date: every file to unpack, with its path in Ubuntu's archive, its size and its SHA-256, and every package to configure, in apt's order. `scripts/ubuntu-packages.sh` (POSIX shell, the same file as in bayan-web) has three commands. `lock` writes the lock with Docker: it runs `apt-get update --snapshot` in the base image, which checks the snapshot's index against Ubuntu's signature with the image's own keyring, takes every path, size and hash from that verified index, and refuses a snapshot date before the image's creation or not before the cutoff, and a plan that removes a package. `fetch` puts every file into a folder that `actions/cache` keeps between runs: a file already there is checked, a missing one is downloaded from the snapshot, else Launchpad's librarian, else the live archive, over HTTPS only, and checked against the lock's size and SHA-256 before it is moved in; a mismatch stops the job without trying another source. `install` replays the plan with dpkg, without apt and without network, and checks the result. Only runs on `main` save the cache, after `fetch` and before `install`; pull requests and the merge queue only read it, and its key changes with the lock (to throw a bad cache away, change `ubuntu-packages-v1` in the key, in all three jobs). The gate's tests above keep the jobs on the lock's base image, and the workflow `Ubuntu packages` (`.github/workflows/ubuntu-packages.yml`, not a required check: it runs when the lock, the script or that workflow changes) runs `lock` again from the lock's header and fails unless the result is the committed lock, byte for byte. The monthly dependency session moves the base image, the snapshot date and the lock together, with the same image and date as bayan-web (see the docs repository's `developer/dependency-update-runbook.md`): it writes the new digest, with the image's creation time, in all three jobs, and runs `sh scripts/ubuntu-packages.sh lock --from deps/ubuntu-packages.lock --image <image>@sha256:<digest> --snapshot <date> --cutoff <cutoff> --output deps/ubuntu-packages.lock` (Docker; in a cloud session, start its daemon first with `nohup dockerd >/tmp/dockerd.log 2>&1 &`; the command then uses the session's proxy). A newly requested package needs the justification of ground rule 5; the packages that apt adds as dependencies do not. The packages' maintainer scripts run as root in the container while dpkg installs them, as they did under apt: the exception to ADR-0017 rule 6 that the amendment names. To reproduce a job's environment, run the base image, then the script's `fetch` and, as root, `install`.
- **REUSE** (for the `reuse lint` workflow) is pinned in `.github/reuse/`: `requirements.txt` holds REUSE 6.2.0 and its dependencies, and `build-requirements.txt` the build backend poetry-core 2.5.0, all at exact versions with SHA-256 hashes. The workflow installs them with `pip --require-hashes`, as prebuilt wheels only, except REUSE itself, which is built from its hash-pinned source archive without build isolation, so nothing else is downloaded during the build. Both files are identical in all five BayanDocs repositories and match `req_reuse` and `req_poetry_core` in `docs/scripts/cloud-environment-setup.sh`; they change only in the monthly dependency session, in all five repositories together.
- Upgrades happen only in the monthly dependency session, following the docs repository's `developer/dependency-update-runbook.md`.

In BayanDocs cloud sessions the tools are preinstalled at pinned versions by `docs/scripts/cloud-environment-setup.sh`; run `bayandocs-tools` to list them. From version 2026-10-04.3 of that script on, it also runs `scripts/dev-setup.sh` (`bayandocs-tools` then lists `desktop-tools`); otherwise run it yourself at the start of a session (it reuses the preinstalled Qt). Either way, this repository's pinned CMake, Ninja, clang-format and clang-tidy are deliberately not on the default `PATH`, because CMake 4 refuses projects that declare `cmake_minimum_required` below 3.5 and other repositories may build such projects: load `. ~/.local/share/bayandocs/desktop-tools/env.sh` in every new shell before building (if your shell state does not persist between commands, start each command with it). If any other tool is missing, install the version pinned there (never a newer one) and mention it in the pull request.
