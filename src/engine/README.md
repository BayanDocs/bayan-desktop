# The engine integration layer

This directory connects the desktop shell to the BayanDocs engine. The shell talks to the engine only through the engine's C interface and the JSON protocol of [engine-protocol.md](https://github.com/BayanDocs/docs/blob/HEAD/specs/engine-protocol.md) (ADR-0012):

- `engine.h` and `engine.cpp` hold `bayan::Engine`, a C++ wrapper over the C interface. It owns the engine instance, sends protocol messages, and moves the engine's replies and events from the engine's thread to the Qt main thread.
- `protocol.h` and `protocol.cpp` hold the protocol's data as C++ values (pages, overlays, the accessibility tree, input events) and their strict parsers: every message from the engine is checked before the shell uses it.
- `stub/` holds a stub engine, `stub/bayan_engine_stub.cpp`, that implements the C interface with one fixed test page, so that the shell can be built and tested without Rust, together with copies of two files of bayan-core's C SDK, from the commit pinned in `deps/bayan-core.json`: `stub/include/bayan_ffi.h`, the C header that bayan-core generates with cbindgen, which the stub compiles against, and `stub/schema/engine-protocol.schema.json`, the protocol's JSON Schema, which the tests check messages against. Both are byte for byte the SDK's (see [The copies of the header and the schema](#the-copies-of-the-header-and-the-schema)). The stub does what the header documents, as the real engine does: it handles messages and tiles in order on its own thread, `bayan_render_tile` returns `BAYAN_STATUS_WRONG_THREAD` inside any engine's callback, and an engine freed inside its own callback delivers nothing more. It sends only messages that the schema allows, and keeps its test switches for the shell's error paths, described at the top of the file.

The CMake option `BAYAN_ENGINE` chooses the engine: `stub` (the default) compiles the stub into the app, and `sdk` links the real engine from bayan-core's C SDK (work package CORE-007), whose directory is given in `BAYAN_ENGINE_SDK_DIR`.

## The C SDK layout bayan-desktop expects

This is the contract between this repository and CORE-007: the SDK is a directory (unpacked from an archive or built locally) that contains the following files. The build reads the header and the library; the test `engine.sdk_copies` reads the header and the schema, to compare them with the copies in `stub/`. Nothing else in the SDK is read.

| File | Platforms | What it is |
| --- | --- | --- |
| `include/bayan_ffi.h` | all | The C header of the engine, generated by cbindgen. `stub/include/bayan_ffi.h` is a copy of it. |
| `schema/engine-protocol.schema.json` | all | The JSON Schema (draft 2020-12) of the protocol's messages, generated from the engine's Rust types. `stub/schema/engine-protocol.schema.json` is a copy of it. |
| `lib/libbayan_ffi.so` | Linux | The engine as a shared library. Its SONAME must be `libbayan_ffi.so`; without one, programs would record the absolute path where they were linked instead. A Rust `cdylib` gets no SONAME by default, so CORE-007 passes `-Wl,-soname,libbayan_ffi.so` to the linker. |
| `lib/libbayan_ffi.dylib` | macOS | The engine as a dynamic library. Its install name must be `@rpath/libbayan_ffi.dylib`, so that programs look for it along their run path. By default a Rust `cdylib` records the absolute path where it was built, so CORE-007 passes `-Wl,-install_name,@rpath/libbayan_ffi.dylib` to the linker. |
| `bin/bayan_ffi.dll` | Windows | The engine as a DLL. |
| `lib/bayan_ffi.lib` | Windows | The DLL's import library, which the linker needs. The name Rust gives it, `bayan_ffi.dll.lib`, is accepted too. |

The library exports the functions declared in `bayan_ffi.h` with C linkage and the platform's standard C calling convention, and nothing in it may require the caller to use Rust. Debug symbols (`.pdb`, `.dSYM` or split DWARF files) may sit next to the library and are not needed to build.

How the app is built against it (`src/engine/CMakeLists.txt`): the library becomes an imported shared library target (`IMPORTED_LOCATION` is the `.so`, `.dylib` or `.dll`; on Windows `IMPORTED_IMPLIB` is the import library), and every program that uses the engine links it dynamically:

- **Linux and macOS:** CMake records the SDK's `lib` directory in the run path of the programs it builds, so `bayan-desktop` and the tests find the library where the SDK is unpacked, without copying it.
- **Windows:** Windows looks for DLLs next to the program, so the build copies `bayan_ffi.dll` next to `bayan-desktop.exe` and every test program after linking them (`bayan_deploy_engine_runtime`). Only the engine's DLL is copied: Qt's DLLs stay in Qt's installation (on `PATH`), so that Qt keeps finding its plugins.

Packaging the library into installers (an app bundle's `Frameworks` folder, the Windows installer, Linux packages) belongs to the packaging work packages, not to this scaffold.

## The copies of the header and the schema

`stub/include/bayan_ffi.h` and `stub/schema/engine-protocol.schema.json` are copies of the SDK's `include/bayan_ffi.h` and `schema/engine-protocol.schema.json`, as the SDK built from the bayan-core commit pinned in `deps/bayan-core.json` has them (bayan-core keeps both in its repository, as `crates/bayan-ffi/include/bayan_ffi.h` and `crates/bayan-engine/protocol/engine-protocol.schema.json`). They are never edited: whenever the app is built against an SDK, the test `engine.sdk_copies` (`tests/engine-sdk/compare-copies.cmake`) compares both byte for byte with the SDK's, and fails if either differs. CI runs it on Linux, macOS and Windows and in the sanitizer job against the SDK it builds from the pin, so moving the pin without updating the copies fails. The header keeps cbindgen's formatting, so clang-format and clang-tidy leave it out (`CMakeLists.txt`, `.clang-tidy`).

When the pin moves, build the SDK from the new commit with `scripts/build-engine-sdk.sh`, copy its two files over the copies unchanged, and adapt the stub and the tests to what changed in them; then run `cmake --workflow --preset verify` and `BAYAN_REQUIRE_MOCK_DOCUMENT=1 scripts/test-engine-sdk.sh --sdk build/bayan-core-sdk`.

The tests use the schema in three ways:

- `tests/support/protocolschema.h` is a strict checker for it, written with Qt's JSON classes, so that no JSON Schema library is needed. It implements exactly the parts of JSON Schema that the generated schema uses, and loading a schema that uses any other keyword or format fails, so that a later schema cannot pass unchecked; `unit.protocol_schema` tests it.
- Every message that a test hands the shell as if from the engine goes through `tests/support/enginemessages.h`, which checks it against the schema first, so that the tests only feed the shell messages the engine could send.
- `engine.c_interface` (`tests/tst_cinterface.cpp`) holds a conversation with the engine the build links, through the C interface and a callback of its own, that makes it send every kind of message it has, and checks each one: for the stub, that it sends only what the real engine could send; for the real engine, that the checker accepts what the engine really sends.

## Testing against an SDK

`scripts/test-engine-sdk.sh` builds bayan-desktop against an SDK with `BAYAN_ENGINE=sdk` and runs the tests that use the engine (the `engine-sdk` workflow preset, or `engine-sdk-msvc` on Windows). CI runs it on Linux, macOS and Windows against two SDKs:

- **A stand-in SDK:** without arguments, the script builds the stub with `tests/engine-sdk/` as a shared library in exactly the layout above, exporting only the functions of `bayan_ffi.h`, and installs it into `build/stand-in-sdk/sdk`. This checks how the app finds and links an SDK.
- **The real engine:** `scripts/build-engine-sdk.sh` builds bayan-core's C SDK (CORE-007) from the commit pinned in `deps/bayan-core.json` into `build/bayan-core-sdk`, and `scripts/test-engine-sdk.sh --sdk build/bayan-core-sdk` tests against it. Its mock document has the editable line and the accessibility tree that the input-method and accessibility tests need; with the stub those tests skip, and with `BAYAN_REQUIRE_MOCK_DOCUMENT=1` (as in CI) they fail instead of skipping.
- **The real engine under the sanitizers:** `scripts/test-engine-sdk.sh --sdk build/bayan-core-sdk --sanitizers` (Linux) builds the app and its tests with AddressSanitizer and UndefinedBehaviorSanitizer (the `engine-sdk-asan` workflow preset) and runs the tests that use the engine against the real engine. CI's sanitizer job does so with `BAYAN_REQUIRE_MOCK_DOCUMENT=1`, after it has run every test against the stub under the sanitizers (the `asan` preset). The engine's library is not instrumented: the sanitizers watch the shell's side of the boundary, where the engine's thread calls the shell's callback, the callback copies each message and hands it to Qt's main thread. The engine's library is loaded into the instrumented test programs, so its allocations go through AddressSanitizer's allocator too (which catches, for example, memory freed twice), although its own reads and writes are not checked, and LeakSanitizer reports what is still allocated when a test program ends; every test frees its engines. Suppressions in `tests/lsan-suppressions.txt` may only name third-party libraries; a leak inside the engine is a bayan-core problem, to report rather than suppress.

To use any other SDK, such as one downloaded from bayan-core's CI, set `BAYAN_ENGINE_SDK_DIR` to its directory and run `cmake --workflow --preset engine-sdk` (on Windows, `engine-sdk-msvc` from a Visual Studio developer environment), or `scripts/test-engine-sdk.sh --sdk <directory>`.
